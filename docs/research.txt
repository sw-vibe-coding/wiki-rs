6) Storage Evolution (Critical Architecture Story)
Let’s trace storage approaches in order.

Phase 1: Flat File Storage (1995–early 2000s)
Model:

/wiki-pages/
  PageOne.txt
  PageTwo.txt
Examples:
WikiWikiWeb

UseModWiki

Pros:
Simple

Easy backup

Human-readable

Cons:
Poor scalability

No indexing

Concurrency issues

Phase 2: File + Metadata + Diffs
Enhancements:

Revision files

Change logs

Diff storage

Example:
MediaWiki (2002)

👉 Transition system: still file-ish thinking, but evolving

Phase 3: Database-backed Wikis (2000s)
Model:

Pages table
Revisions table
Users table
Examples:
MediaWiki

JSPWiki (optional DB)

MoinMoin (hybrid)

Pros:
Scalability

Querying

Permissions

Cons:
More complex

Migration issues

Phase 4: Hybrid File + DB + Caching
Used by large systems:

File storage for content blobs

DB for indexing

Cache layers (memcached)

Example:
Wikipedia stack

Phase 5: Single-file / Client-side Storage (2004+)
TiddlyWiki model:
Entire wiki = one HTML file

Stored:

Local file

Browser memory

Pros:
Portable

Offline-first

Cons:
Sync issues

Multi-user hard

Phase 6: Browser Storage APIs (2010s)
Storage options:

localStorage

IndexedDB

Used by:

Modern client-heavy wikis

Phase 7: Git-backed Wikis
Examples:
Gollum

GitHub Wikis

Model:

Git repo = wiki
Each page = file
History = commits
Pros:
Versioning built-in

Branching

Cons:
Not user-friendly for non-devs

Phase 8: CRDT / Real-time Collaborative Wikis (Modern)
Examples:

Notion

TiddlyWiki

Storage:

CRDTs (Conflict-free Replicated Data Types)

Event logs

Operational transforms

Characteristics:
Multi-user real-time editing

Offline sync

Eventually consistent

Trend	Wiki Equivalent

Databases →	MediaWiki
Browser apps →	TiddlyWiki

Approach	Strength	Weakness
File-based	Simple	Not scalable
DB-based	Scalable	Complex
Client-side	Portable	Sync issues
Git-based	Versioned	UX friction
CRDT	Real-time	Complex logic
